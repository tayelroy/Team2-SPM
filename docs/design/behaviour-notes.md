## Sequence 2 — venue temporarily unavailable; change or cancel one venue (SG2-80/81/83, built)
- `POST /api/venues/:venueId/blocks`: `server/src/venues/blocks.ts`, `server/src/db/venueBlocks.ts`.
- Triggers `venue_unavailability_stamp`, `venue_unavailability_flag_bookings`, table `venue_booking_disruptions`, view `venue_affected_bookings`, RPC `list_venue_unavailability`: `202610100001_venue_temporary_unavailability.sql`.
- Client: `client/src/venues/VenueBlocks.tsx`, `blocksApi.ts`.
- Replacement uses existing `POST /api/venue-booking-requests` with optional `replaces_booking_id`, and existing `POST /api/venue-booking-requests/:requestId/decision`. The API checks the reference is a current confirmed booking of the same assigned event (`changeableBookings`); a booking the venue's unavailability affects needs no `change_reason`, any other booking must give one (SG2-83 AC4). There is no new replacement endpoint.
- `202610170001_venue_replacement.sql`: `venue_disruption_notify` notifies the current Coordinator on each new flag; Preparation/Confirmed returns to Planning, clears confirmation and records history, with an Organiser notice. Other event details and the original booking remain. Earlier flags are not retrospectively announced.
- Approval uses `decide_venue_booking_request` and internal `release_replaced_booking` (latest body `202610210002_venue_booking_change_cancel.sql`) in one transaction: create new confirmed booking, approve new request, release old booking/cancel its request, update the primary pointer and write history/notices. A pending replacement reserves nothing.
- SG2-83 (`202610210002_venue_booking_change_cancel.sql`): `POST /api/venue-bookings/:bookingId/release` `{reason, also_cancel?}` (`server/src/venues/bookings.ts`, adapter `server/src/db/venueBookings.ts`, permission `venue_bookings.release` = Event Coordinator only) calls RPC `release_venue_bookings`: cancels the named booking and only the other bookings of the same event the coordinator names, withdraws a pending change that would replace a cancelled booking, notifies Coordinator + Organiser (`venue_booking_released`) and every Venue Staff account (`venue_booking_cancelled`). A change request is a replacement request with `change_reason`; trigger `venue_change_request_check` refuses one that names a booking of another event or one already over, trigger `venue_change_requested` writes history and notifies Venue Staff (`venue_change_requested`). Both paths call `return_event_to_planning_for_venue`, which returns a Preparation/Confirmed event to Planning (a cancellation also marks `venue_recheck` outstanding) and notifies Organiser and Coordinator.
- Booking lists expose `affected_by` and pending `replacement`; arrangements count affected confirmed bookings. `confirm_event` (latest body `202610290001_requested_equipment_outstanding.sql`, earlier `202610170002_confirmation_rechecks_and_disruptions.sql`) keeps both disruption checks, the persisted venue/equipment/registration rechecks and, since SG2-94, the safety approval. Client notification rendering supports `venue_unavailable` at 61416cc.

## Code notes
- `submitEventRequest` writes `needs_clarification → submitted` and `rejected → submitted` when a coordinator is already assigned. It also writes `draft → submitted` in that branch (`SUBMITTABLE_STATUSES` includes `draft`), but a draft cannot hold a coordinator (`COORDINATOR_ASSIGNABLE_STATUSES` excludes `draft`), so that edge is drawn but not reachable in practice.
- No code table enforces the graph. `updatePlanning.ts` refuses only `cancelled`/`completed`/`rejected` (L440) and refuses edits to locked fields on Preparation/Confirmed (a change request is needed, SG2-66 AC6), but sets `status = 'planning'` on any edit with arrangement impact and on the first edit of an approved event (L497–500). `updateEventPlanningFields` filters the write on `event_id` + `coordinator_id` only. So any non-terminal event the handler accepts (incl. `submitted`, `under_review`, `needs_clarification`, `safety_rejected`) would return to `planning` on an impacting edit; arrangement impact needs a date shift or attendance increase against a live venue or equipment arrangement, which such events rarely have. The diagram draws the awaiting_safety_check and approved edges plus a note covering the rest. Preparation/Confirmed cannot reach `planning` this way, because date and attendance are locked there.
- The database enforces two status rules itself: `safety_approval_gate` (only an Approve decided during the wait reaches `preparation`) and `keep_cancelled_events_cancelled` (a cancelled event never changes status again).
- Cancellation: `request_event_cancellation` refuses `draft`, `completed`, `cancelled` and `rejected` events; `cancel_event` also needs the caller to be the assigned coordinator, so an `unassigned` event (no coordinator) cannot be cancelled until it is assigned. A draft is removed with `DELETE /:id` instead.
- `confirm_event` answers a request on an Approved, Planning, Awaiting Safety Check or Safety Rejected event with the outstanding items (safety included) and only confirms an event in `preparation`.
- SG2-88 (assign/reassign as Lead) and SG2-89 (oversight) are Done and merged; `PATCH /:id/coordinator` supplies assignment/reassignment and `GET /api/coordinator-overview` the oversight view. This does not substitute for per-criterion hosted acceptance.
- SG2-80 originally only flagged affected bookings. SG2-81 adds `venue_unavailable` notices on new flags and the Preparation/Confirmed return to Planning; the availability calendar still reads `venue_affected_bookings`.
